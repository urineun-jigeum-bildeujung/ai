# 재구매 SHADOW 배치 검증 결과와 후속 조건

## 이번 단계 결론

추가 격리 DB나 수동 Job을 만들지 않고 **로컬 변경 입력·롤백 검증으로 이번 단계를 마무리한다.** EKS에서 확인한 범위는 첫 SHADOW 적재와 동일 실행 ID 재시도의 멱등성까지다. 로컬에서 확인한 변경 반응과 실패 시 롤백을 EKS 검증으로 표기하지 않는다. 인프라에 지금 추가 작업을 요청하지 않는다.

추후 실제 주문이 새로 생기고 다음 관측 컷·실행 ID가 확정되면 AI가 변경 전후 대상 키를 비교한다. 정기 CronJob과 사용자 노출은 별도 승인 전까지 보류한다.

## 추후 클라우드 검증이 필요할 때의 조건

### 1. 변경 주문 반영 — 실제 새 주문이 생기면 확인

새 실제 주문이 적재될 때까지 공유 원천 DB와 기존 SHADOW 배치를 수정하지 않는다. 변경 반응만 고립해 확인해야 하는 경우에는 별도의 격리 입력을 준비한다. 기준 입력과 변경 입력의 차이는 유효 결제 주문 1건으로 제한하고, 대응 주문상품·결제 상태 이력·일관된 상품군/반려동물 연결을 포함한다. 실제 서비스 원천에 테스트 주문을 삽입하지 않는다.

AI는 두 입력에 각각 다른 `publication_id`와 명시적 관측 컷을 부여한다. 관측 컷은 각 원천 추출 시각 이하로 고정한다. 실행 전, 대상 사용자·상품군의 구매 사건/피처가 어떻게 달라져야 하는지 기대값을 기록한다. **결과 행 수가 같더라도 해당 대상 키의 예측값은 달라질 수 있으므로**, 총 건수만 비교하지 않는다.

추후 인프라의 수동 Job이 필요하면 AI가 입력 연결·고정 이미지/모델 버전·새 실행 ID를 먼저 전달한다. CronJob은 활성화하지 않는다. AI는 두 실행의 로그, 배치 상태/건수, 대상 키의 예측값, 사용자 최신 조회 뷰 0건을 읽기 전용으로 대조한다. 예측값이 기대와 다르거나 원천 이외 조건이 달라지면 검증 실패로 남긴다.

### 2. 실패 시 미발행 — 공유 결과 DB에 고의 오류를 주입하지 않음

현재 로컬 PostgreSQL 테스트는 결과 COPY 단계 오류가 발생하면 배치와 결과가 함께 롤백됨을 확인한다. 클라우드에서도 확인하려면 AI가 **별도 격리 결과 DB**와 고유 실행 ID를 준비한 뒤, 안전한 실패 사례와 사전/사후 조회를 확정한다. 인프라는 그 입력만 가리키는 수동 Job을 실행하고 종료 코드·단일 실패 로그를 전달한다. AI는 격리 결과 DB에서 해당 실행 ID의 배치 0건·예측 0건을 확인한다. 비밀번호나 원천 행을 로그·이슈에 남기지 않는다.

격리 결과 DB를 준비할 수 없다면 이 클라우드 장애 주입은 보류하고, 로컬 롤백 검증과 실제 EKS 성공/멱등성 검증을 **서로 다른 근거**로 보고한다. 연결 실패만 재현한 Job을 원자적 롤백 검증으로 해석하지 않는다.

## 역할과 운영 전환 게이트

| 담당 | 후속 작업 |
| --- | --- |
| AI | 새 원천이 생기면 기대값·새 실행 ID/관측 컷 준비, 모델/피처 검증, 결과 DB 대조, 사용자 노출 승인 판단 |
| 인프라 | 지금 추가 작업 없음. 후속 수동 Job이 필요하면 AI가 고정한 입력으로 실행하고, 승인 뒤 GitOps CronJob·재시도/알림 설정 |
| BE/FE | 승인된 사용자별 조회 경로와 인증·표시 계약 연결 |

현재 상태는 내부 `SHADOW` 검증이다. 모델 성능·확률 보정과 사용자별 조회 계약이 승인되기 전에는 `PUBLISHED`로 전환하거나 정기 CronJob을 활성화하지 않는다. 기존 완료 Job과 결과 배치는 보존한다.
