# 재구매 추론·아티팩트 계약

## 지금 코드에서 확정된 모델 입력

두 후보 모델은 같은 과거 구매 피처 네 개를 사용한다. 입력 행 하나는 **특정 사용자·예측 대상의 구매 시점(`anchor_at`)에서 만들었던 상태**를 뜻한다. 정답이나 그 이후의 주문은 입력에 넣지 않는다.

| 피처 | 의미 | 허용값 |
| --- | --- | --- |
| `history_interval_count` | 해당 시점까지 계산 가능한 과거 구매 간격 수 | 결측 없는 0 이상 정수 |
| `history_median_days` | 과거 간격의 중앙값 | 0 이상 유한한 수 또는 과거 간격이 없을 때 결측 |
| `history_relative_mad` | 과거 간격의 상대적 불규칙성 | 0 이상 유한한 수 또는 계산할 수 없을 때 결측 |
| `user_prior_order_count` | 해당 시점 이전 사용자 주문 수 | 결측 없는 0 이상 정수 |

아티팩트에는 사용한 피처의 **이름과 순서**, `feature_generation_version`, 모델 종류, 확률의 기준 기간, 저장 라이브러리 버전, 모델 파일 SHA-256, 이들을 합친 `artifact_id`를 기록한다. 피처 버전은 과거 간격과 주문 수의 **계산 의미**를 나타내며, 생성 규칙을 바꿀 때 올리고 재학습해야 한다. 저장된 버전이 현재 코드와 다르면 로드를 거절한다. 버전 값은 사람이 관리하는 계약이므로 코드 의미가 자동으로 같다는 증명은 아니며, 학습·운영 피처 일치 테스트도 함께 유지한다. 버전 필드가 없던 이전 아티팩트 형식은 호환되는 것으로 간주하지 않는다. AFT는 확률 계산에 필요한 손실분포와 scale도 보존한다. XGBoost는 JSON, LightGBM은 네이티브 텍스트 형식으로 저장한다. Python pickle은 사용하지 않는다. 기존 경로를 덮어쓰지 않고 임시 디렉터리에서 파일을 완성한 뒤 옮긴다.

`load_model_artifact()`는 파일 해시·메타데이터 ID·라이브러리 버전·모델 내부 피처 순서를 확인한다. `predict_artifact_probability()`는 저장 전후 동일 입력의 확률이 같은지 테스트할 수 있도록 한다. 아티팩트 ID는 **버전 추적용 내용 지문**이지 서명이나 접근 제어가 아니다. 배포 저장소의 권한·불변성 관리는 별도로 필요하다.

## 현재 출력의 정확한 의미

현재 함수가 반환하는 값은 **마지막 구매를 기준으로 30일 이내 재구매할 누적확률**이다. 예를 들어 마지막 구매 후 이미 20일이 지난 사용자에게 이 값을 그대로 보여주며 “앞으로 30일 내 재구매 확률”이라고 말하면 틀린다. LightGBM은 고정 30일 분류 확률이고, AFT는 학습된 시간 분포를 30일 시점에서 계산한 확률이다.

AFT의 기본 시간 척도 예측 `exp(raw margin)`은 모든 분포에서 평균·중앙 재구매일을 뜻하지 않는다. 따라서 이 값을 `predicted_purchase_date`로 곧바로 바꾸지 않는다. 현재 확률을 신뢰도(`confidence_score`)로 표시하지도 않는다. 확률과 예측 오차 범위·개별 결과의 신뢰도는 서로 다른 개념이다.

## 백엔드 연동 전에 확정할 입력·출력

운영 요청에는 최소한 `user_id`, 선택적 `pet_id`, `target_scope`와 `target_id`, 마지막 유효 구매의 `paid_at`, 계산 기준 시각 `as_of_timestamp`가 필요하다. AI 쪽은 이 시각 **이전의 유효 주문만** 사용해 네 피처를 재구성해야 한다. 실제 주문·취소·반품을 네 피처로 바꾸는 운영 파이프라인은 아직 구현되지 않았다. `pet_id`가 없으면 사용자 단위로 처리할지, 한 사용자의 여러 반려동물 주문을 어떻게 구분할지도 백엔드와 계약해야 한다.

`build_valid_order_items()`는 백엔드 `orders`·`order_items`의 **현재 상태**를 결합한다. 주문 상태가 `PAID`·`PARTIAL_REFUND`, 상품 상태가 `PAID`·`PARTIAL_RETURN`이고 `quantity - cancelled_quantity - returned_quantity >= 1`인 상품 행을 남긴다. 주문·상품 키, 상태값, 시간대가 포함된 `paid_at`, 수량·외래키의 모순을 검사하며 주문 상품 원본을 수정하지 않는다. `pet_id`와 구매 당시 `product_group_id_snapshot`·`is_replenishable_snapshot`, `purchase_type`을 결과에 보존한다. 비반복 소비 상품도 사용자 전체 과거 주문 수에 필요하므로 이 단계에서는 제거하지 않는다. 이 결과는 아직 **구매 상품 행**이며 상품군·반려동물 단위의 구매 사건으로 합쳐진 것이 아니다.

`build_current_features_from_valid_purchases()`의 입력은 구매 상품 행이 아니라 **범위가 확정된 유효 구매 사건 전체**다. 각 행에는 `user_id`, `order_id`, `product_id`, 시간대가 포함된 `paid_at`만 들어간다. `build_valid_order_items()`의 결과를 그대로 넘기거나 상품군 ID를 임의로 `product_id`로 바꾸면 안 된다. 동일 주문의 여러 상품 행 병합, `product_group_id` 매핑, `pet_id` 구분은 아직 후속 계약이다. 원본 주문 상태나 반려동물 열을 묵시적으로 무시하지 않고 오류를 반환한다. 다른 상품 주문도 `user_prior_order_count`에 필요하므로 예측 대상 상품의 주문만 전달해서는 안 된다.

현재 상태 스냅샷만으로는 과거 기준 시각 *당시*의 주문 상태를 재구성할 수 없다. 예를 들어 예측 이후 반품된 주문을 오늘 상태로 다시 읽어 과거 예측을 재현하면 미래 정보를 사용하게 된다. 따라서 이 정규화 함수는 현재 운영 입력용이며 과거 학습 샘플 재생에는 상태 변경 이력 또는 시점별 스냅샷이 별도로 필요하다.

함수는 `as_of_timestamp` 이후 구매를 제외하고, 사용자·상품별 **마지막 유효 구매 사건**마다 기존 학습 함수로 계산한 네 피처, `anchor_at`, `elapsed_days`를 반환한다. 동일 사용자·상품의 서로 다른 주문이 같은 결제 시각이면 시간상 선후를 임의로 정하지 않고 오류를 반환한다. `elapsed_days`는 현재까지 지난 기간일 뿐, 함수가 미래 조건부 확률이나 구매 권장일을 계산한다는 뜻은 아니다. 운영에서 이력을 다시 계산할 때도 입력 사건 집합과 기준 시각을 함께 기록해야 재현할 수 있다.

이 함수가 보장하는 것은 **계산 코드의 일치**다. 현재 후보 모델은 UCI의 동일 `product_id`와 주문 기록 시각으로 학습했지만, 실제 서비스는 `product_group_id`와 결제 완료 시각을 사용할 계획이다. 두 데이터의 상품 식별·시각 정의·분포가 같다는 뜻은 아니므로, 운영 데이터 매핑과 재학습·Validation 없이 현재 모델을 바로 서비스에 적용하지 않는다. 아티팩트가 피처 계산 규칙 버전을 저장하더라도, UCI 상품 ID와 실제 서비스 상품군 ID의 의미 차이를 자동으로 해결하지는 못한다.

운영 결과에는 대상 키, `as_of_timestamp`, `artifact_id`, 결과 상태와 계산 시각을 포함해야 한다. 날짜 안내를 제공한다면 구매 경과일을 반영한 시간 분포의 적절한 대표값·구간을 먼저 정의하고 검증해야 한다. 이력이 부족하거나 필수 주문 정보가 빠지면 근거 없는 날짜 대신 명시적인 상태와 fallback을 반환한다. 이 문단은 **연동 전 요구사항**이지 이미 제공되는 API 명세가 아니다.

## 배포 전 남은 결정

1. 세 rolling Validation fold에서 AFT와 LightGBM의 우위가 바뀌고 사용자 Bootstrap 구간도 0을 가로지른다. 이번 아티팩트 기능은 두 후보 모두 지원하지만 **운영 모델은 아직 선정하지 않는다**.
2. 피처 생성 규칙의 버전 관리와 현재 주문 상태의 유효 수량 판정은 추가했다. 주문 상태 정정 시 과거 기준 시점과 현재 예측을 어떻게 재계산할지는 여전히 정해야 한다.
3. 현재 시점에서의 조건부 재구매 확률, 날짜·예측구간, 낮은 신뢰도 및 콜드스타트 응답을 Validation에서 검증한 뒤 화면 문구를 확정해야 한다.
4. 모델 저장 위치·접근 권한·배포 버전 고정·롤백·기동 시 로딩 실패 정책과 BE↔AI API 계약은 후속 작업이다. 아티팩트 테스트 통과만으로 배포 준비 완료라고 판단하지 않는다.
