# 재구매 공용 클라우드 데이터 읽기·결과 적재 계약 초안

상태: **팀 간 확인 전 초안**. 이 문서는 재구매 파트에만 적용한다. 백엔드와 AI가 HTTP API로 예측을 주고받는 방식은 현재 계획이 아니다. 백엔드가 공용 클라우드에 적재한 데이터를 AI 작업이 직접 읽고, AI가 파생 데이터와 결과를 직접 적재한다. 백엔드는 합의된 결과 저장 영역을 조회한다.

## 확인된 범위와 아직 확인되지 않은 범위

| 구분 | 현재 확인된 내용 | 확인이 필요한 내용 |
| --- | --- | --- |
| 원천 | `orders`, `order_items`, 상품군·반려동물 정보는 백엔드가 관리한다. | 실제 클라우드 저장소/DB, 스키마명, 접근 경로, 갱신 주기 |
| AI 읽기 | 재구매 라벨과 피처는 결제된 주문 원천에서 만든다. | AI 계정의 읽기 권한, 시점별 상태 이력 제공 방식 |
| AI 쓰기 | 재구매 파생 데이터와 예측 결과를 AI가 직접 적재한다. | 전용 스키마/테이블 생성 권한, 적재 방법과 결과 보존 기간 |
| BE 사용 | 백엔드는 적재된 최신 유효 결과를 읽는다. | 조회 조건, 결과가 없거나 오래됐을 때의 처리 |
| 실행 | 학습과 추론은 저장소의 데이터 컷을 기준으로 실행한다. | 배치 일정, 주문 변경 후 갱신 지연 허용치, 재시도 책임 |

이전 [재구매 HTTP API 초안](https://app.notion.com/p/3d086270a2548125892fcbe59b13ce91)의 `POST /recalculations`와 `GET /predictions`는 현재 연동 방식의 확정 계약이 아니다. 별도 API 서버가 필요해지는 경우에만 다시 검토한다.

## 원천 데이터 읽기

공통 [AI 통합 데이터 스키마](https://app.notion.com/p/AI-3c386270a254803f92b8eebaabb9cdf1)에 적힌 필드 중 재구매 파트가 우선 확인할 것은 아래와 같다. 실제 저장소의 물리적 이름과 타입은 백엔드의 샘플로 대조해야 한다.

| 원천 | 재구매 파트가 필요한 값 | 사용 이유 |
| --- | --- | --- |
| `orders` | `order_id`, `user_id`, `paid_at`, `order_status`, `purchase_type`, `updated_at` | 결제 시점, 유효 주문, 정기결제 구분 및 정정 확인 |
| `order_items` | `order_item_id`, `order_id`, `product_id`, `product_group_id_snapshot`, `category_code_snapshot`, `is_replenishable_snapshot`, `pet_id`, `quantity`, `cancelled_quantity`, `returned_quantity`, `item_status`, `updated_at` | 사용자·반려동물·상품군별 유효 구매 사건 생성 |
| `product_groups`·`product_master` | 상품군 ID와 상품-상품군 관계 | 서로 다른 SKU의 동일 상품군 재구매 식별 |
| `pet_profile` | `pet_id`, `user_id` | 주문의 반려동물 소유 관계 검증. 재구매에 필요 없는 민감한 건강 정보는 기본 조회 대상에서 제외 |
| 주문 상태 이력 또는 시점별 스냅샷 | 정정 전후 상태와 적용 시각 | 과거 학습 시점에 미래 반품 정보가 새지 않도록 재현 |

`paid_at`과 기준 시각은 시간대를 포함해야 한다. 같은 주문의 같은 상품군·반려동물에 속한 여러 상품 행은 한 구매 사건으로 묶고, `pet_id`가 없는 행을 특정 반려동물에게 임의 배정하지 않는다. 비반복 상품은 상품군 재구매 대상에서 제외할 수 있지만 사용자 전체 주문 수를 계산하는 원천에서는 무조건 삭제하지 않는다. 취소·반품 후 유효 수량이 0인 행은 유효 구매가 아니다. 현재 구현의 자세한 판정은 [추론·아티팩트 계약](INFERENCE_CONTRACT.md)을 따른다.

현재 상태만 보존하는 테이블로는 과거 특정 시점의 주문 상태를 정확히 재현할 수 없다. 백엔드가 상태 변경 이력이나 시점별 스냅샷을 제공할 수 있는지 확인하기 전에는, 현재 데이터를 과거 학습 샘플에 그대로 다시 대입하지 않는다.

## 파생 데이터와 결과 적재

통합 스키마는 `repurchase_training_samples`를 오프라인 파생 데이터, `repurchase_predictions`를 예측 결과로 제안한다. 둘을 공통 원천 테이블과 분리한다. 실제 저장 매체와 스키마명은 아직 미정이다.

| 결과 항목 | 초안에서의 역할 | 현재 구현 상태 |
| --- | --- | --- |
| `user_id`, 선택적 `pet_id`, `target_scope`, 대상 ID | 결과 조회 키 | 상품군·반려동물 구매 사건까지만 구현. 모델 추론 연결 전 |
| `as_of_timestamp`, `last_purchase_at`, `created_at` | 사용한 데이터 컷과 결과 시점 | 운영 결과 적재 전 |
| `prediction_status`, `prediction_method`, 모델·피처 버전 | 결과의 사용 가능 여부와 재현성 | 후보 아티팩트 버전 관리는 구현, 운영 상태값은 미확정 |
| `predicted_date_p50`, 범위, 잔여일 | 구매 시점 안내 | 서비스 데이터에서 검증되지 않음. 필수값으로 약속하지 않음 |
| `probability_7d/14d/30d` | 현재 시점 기준 조건부 재구매 확률 | AFT 계산 코드가 있으나 서비스 상품군 모델·보정·운영 검증 전 |
| `confidence_score/grade`, `reason_codes/message` | 품질 정책 및 설명 | 운영용 근거·신뢰도 정책 미확정. 확률을 신뢰도로 재사용하지 않음 |

`prediction_status=READY`는 단순히 작업이 끝났다는 뜻이 아니라, **해당 범위와 출력 필드가 검증되어 BE가 사용할 수 있다**는 뜻으로 제한한다. 검증 전에는 숫자나 날짜를 임의로 채우지 않는다. `INSUFFICIENT_DATA`, `SUPPRESSED` 등 값이 없는 상태에서는 예측값을 `null`로 두는 기존 통합 스키마 원칙을 유지한다. 처리 중/실패 같은 **작업 상태**와 사용자에게 보여줄 **예측 상태**는 같은 열에 섞지 않는 방향을 제안하며, 저장 구조는 BE와 협의한다.

재실행 시 같은 데이터 컷·대상·모델/피처 버전의 결과를 어떻게 식별할지, 새 실행이 모두 성공하기 전까지 이전 정상 결과를 어떻게 유지할지, BE가 `as_of_timestamp`와 `created_at` 중 무엇으로 최신 결과를 선택할지는 합의가 필요하다. 단순히 매 실행마다 새 행을 넣고 `created_at`이 최대인 행을 고르면, 실패하거나 오래된 데이터 컷으로 생성된 결과가 최신으로 노출될 수 있다.

## 접근·운영 경계

- AI 실행 계정은 필요한 원천에 읽기 권한, 재구매 전용 결과 영역에 쓰기 권한만 받는 것을 제안한다. 원천 주문을 AI가 수정하지 않는다.
- 이메일·이름·전화번호·인증 토큰은 재구매 학습/추론 입력에 포함하지 않는다. 접속 정보는 코드·Git·실험 보고서에 기록하지 않는다.
- 개발·스테이징 합성 데이터와 운영 데이터를 분리한다. 원천 데이터의 사용·보존·이전 조건은 인프라·보안 담당자와 확인한다.
- 주문 변경 감지는 원천의 `updated_at`만으로 충분한지 확인해야 한다. 누락 또는 순서 역전이 가능하면 변경 로그나 주기적 전체 보정이 필요하다.
- 배치 완료 시간과 허용 가능한 결과 지연을 먼저 합의한 뒤 일정·재시도·모니터링 값을 정한다. 현 단계에서 임의의 SLA를 확정하지 않는다.

## 백엔드·인프라와 확인할 결정

1. 공용 클라우드의 실제 데이터 저장 위치와 접근 방식은 무엇인가? AI 읽기 계정/역할과 전용 결과 쓰기 계정을 분리할 수 있는가?
2. `orders`·`order_items`와 상품군/반려동물 키의 실제 스키마, 타입, 시간대, `NULL` 규칙은 초안과 같은가?
3. 취소·부분 반품·전액 환불의 상태 변경 이력 또는 시점별 스냅샷이 있는가? 없다면 과거 학습 재현은 어디까지 가능한가?
4. 결과를 어느 스키마/테이블에 저장하고 누가 생성·마이그레이션하는가? BE는 어떤 키와 상태로 조회하는가?
5. 새 결과 발행 중 실패, 중복 실행, 더 오래된 데이터 컷의 지연 완료를 어떻게 처리할 것인가?
6. 결과가 없거나 오래됐을 때 BE는 이전 정상 결과를 사용할지, 안내를 숨길지? 허용 신선도와 보존 기간은?
7. 결제·취소·반품 후 재계산은 어떤 신호/주기로 시작하는가? 초기에는 주기 배치만 사용할 수 있는가?
8. 스테이징 합성 데이터와 운영 데이터의 분리, 접근 로그, Secret 전달 방식은 무엇인가?

## 다음 이슈의 계약 검증 사례

정상 결제, 부분 취소·반품으로 유효 수량이 남은 주문, 전액 환불, 같은 주문의 동일 상품군 다중 SKU, 반려동물 미지정, 다반려동물 소유 관계 오류, 시간대 누락, 중복 배치 재실행, 오래된 데이터 컷의 늦은 완료, 일부 결과 쓰기 실패를 고정 예제로 만든다. 원천 행 수·구매 사건 수의 보존 관계와 적재 결과의 중복·부분 노출 여부를 검사한다.
